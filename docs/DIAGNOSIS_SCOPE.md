# 诊断范围与实际覆盖（2026-09-21）

状态：本批实现、回归与浏览器验收完成。全面重构目标仍在进行。

## 目标和问题

前两批真实/模拟浏览器验收均发现：评分高且没有建议重试画格时，默认深入诊断返回空报告；页面却显示“已生成结构化审计卡”，并建议再运行相同操作，用户无法在页面主动检查高分画格。

本批保留评分、默认候选和定向诊断的现有架构，不把默认范围悄悄扩大，也不把诊断成功状态或高分等同于全图检查通过。

## 行为

1. 已评分界面提供“建议检查的画格 / 全部已生成画格 / 手动选择画格”。默认仍为建议项。
2. 每次提交显式画格索引；仅完成且有图片的画格可选。手动空选、建议集合为空时按钮禁用，并给出下一步，不请求模型。
3. 显示将诊断的数量，说明首次评审/旧评分失效时可能先重评全部已生成画格，不承诺选择一格一定只调用一次模型。
4. 评审模型选择在评分后仍可见，模型/范围/复选框/重复提交在持久运行状态下锁定；运行期间不提供旧诊断的修复入口。
5. 显示实际有效诊断记录覆盖，如 1/2；按画格去重，并排除图片引用或提示词快照不一致、全局过期的记录。无记录不代表无问题。
6. 保留旧报告兼容：不新增必须迁移的报告字段，不把无法推断的历史请求范围补成“全部”。覆盖数字是现存有效证据，不是最近一次请求数量。
7. 下方旧“任务评审/已通过”改成“视觉评分状态/已评分/评分达标”，提示评分状态不代表逐格深入诊断。

## 实现边界

- diagnosisScope.ts：可选范围、建议筛选、实际覆盖的纯函数。
- DiagnosisScopeControls.tsx：原生有标签的 select/checkbox、44px 控件、数量和调用提示。
- QualityScorePanel：将范围送入持久 start_deep_review 或浏览器旧诊断 flow；显式空数组在调用前拒绝。
- pickDiagnosisCandidates：明确传 [] 不再降级为默认候选，防止意外扩大调用范围；未传范围仍保留默认行为。
- VisualScoreSection / VisualDiagnosisWorkbench / PanelGrid：范围、空态、覆盖与评分语义。

当前范围是“深入诊断”的选择，不是整个评分流程的过滤器。服务端评分缓存和模型/素材指纹逻辑保持原样。当前 URL/提示词相同但外部绕过系统替换文件字节时，客户端无法自行验证内容；服务端运行时仍负责媒体指纹校验。本批不是跨标签页同步或完整任务版本机制。

## 过程中发现并修复的构建启动竞争

首次全量测试、类型检查、lint 通过后，生产构建在并行收集页面数据期间抛 SQLITE_BUSY，栈定位到 db.ts 的 journal_mode 初始化，而不是诊断功能。

- 用真实 better-sqlite3 连接在 Worker 中持有独占锁，原始直接 pragma 稳定触发同样错误；wal-red.log 保留失败证据。
- enableWalMode 在初始化阶段仅对 SQLITE_BUSY 有限重试；检查 WAL 返回值。非 BUSY 错误或重试预算耗尽仍抛错，不吞掉损坏/只读等错误。
- WAL 初始化失败关闭刚创建连接；不关闭其他运行中任务连接。
- 4 条测试覆盖真实竞争释放后成功、非 BUSY 不重试、预算耗尽、未真正启用 WAL 不报成功。
- 后续生产构建使用另一个全新隔离目录，验证不是仅靠复用已初始化数据库绕过问题。

这不是通用 SQL 自动重试，不改任务写入/事务语义，也不保证所有启动锁竞争场景都已解决。
