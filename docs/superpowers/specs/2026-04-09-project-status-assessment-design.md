# 2026-04-09 项目整体状态评估设计

## 目标

基于 2026 年 4 月 9 日时点的仓库状态、核心文档、近期提交和一次新的本地验证，形成一份关于 ComicPedia 当前整体情况的书面评估。本文不是实现计划，而是为了明确项目处在什么阶段、哪些地方已经稳了、风险主要集中在哪，以及下一步最应该优先收什么。

## 范围

本评估覆盖：

- 产品成熟度与功能完成度
- 架构成熟度与模块边界
- 运行时和持久化稳定性风险
- 测试与工具链现状
- 近期工程优先级建议

本评估不覆盖：

- 新功能创意发散
- UI 重设计
- 发版宣传
- 详细实现任务拆解

- 核心文档：`README.md`、`CLAUDE.md`、`docs/ai/handoff.md`

- 2026-04-09 的一次新鲜本地验证：

## 当前状态概述

ComicPedia 已经走出原型阶段。它不再只是若干单点功能的堆叠，而是已经形成了闭环的产品流程和可辨认的系统架构。当前主要问题也不再是“能不能做出来”，而是“这个系统能不能长期正确、稳定、可维护地运行”。

项目目前处在一个偏后期的联调和稳定性收口阶段：

- 主用户流程已经具备端到端闭环
- 架构分层已经存在，而且大体是有意识的
- 回归测试具备实际价值，不是象征性覆盖
- 当前活跃工作主要在修一致性问题，而不是继续铺大功能面

这说明项目已经具备持续迭代基础，但还不适合无顾虑地高速加功能。

## 已经比较稳的基础

### 1. 产品主流程已经闭环

仓库已经支持产品的主生命周期：

- 创建内容
- 可选主题研究
- 生成结构化脚本
- 生成图片
- 运行复审与诊断
- 查看历史与结果页
- 管理角色与系列
- 导出与恢复数据

这意味着项目已经不是在分别证明单个功能点，而是在以一个连接起来的产品形态运行。

### 2. 架构方向基本正确

当前代码结构体现了清晰的职责分离：

- `src/app` 负责页面和 API 路由
- `src/lib/client` 负责浏览器侧生成流程、本地缓存和任务生命周期
- `src/lib/server` 负责 SQLite、图片存储和服务端运行时逻辑
- `src/lib/server/taskOrchestrator` 负责 durable queue 编排和恢复

这说明系统已经不再是页面驱动逻辑为主，而是在向流程驱动逻辑转型。这对于长时运行的生成任务是正确方向。

### 3. 状态模型概念上是成立的

项目已经采用三层状态模型：

- SQLite 作为权威数据源
- IndexedDB 作为本地缓存与高频写入层
- Zustand 作为内存态 UI 状态

对这个产品形态来说，这是正确思路。它同时兼顾了长任务、刷新恢复和实时 UI 反馈，而不是把所有职责压到一个状态层里。

### 4. 回归防线强于普通 side project

当前测试已经覆盖到真正有运营风险的表面，包括：

- task orchestration 与 replay
- task 路由与 actions
- 结果页订阅行为
- VLM 诊断与自动重试
- accuracy 闭环

最新一次本地验证结果也是健康的。这不代表系统已经完全硬化，但说明核心回归是有人持续守着的。

### 5. 文档质量明显高于平均水平

根目录和子模块都存在活跃维护的架构文档与 handoff 文档，这会直接降低后续维护和交接成本，也让后续优先级讨论更容易建立在事实之上。

## 风险集中区

当前主要风险不在功能缺失，而在状态一致性和边界复杂度。

### 1. 双编排路径并存，仍是结构性风险

客户端运行时仍然在 `src/lib/client/taskLifecycle.ts` 及 phase 模块里保留了大量流程逻辑，而服务端又在 `src/lib/server/taskOrchestrator/runtime.ts` 中承担 durable orchestration。

这不是天然错误，但前提是所有权边界必须足够明确。否则同一个任务会同时以不同形式存在于：

- 页面状态
- Zustand 内存态
- IndexedDB 缓存
- SQLite 状态
- durable queue job 状态

最近修的 Result 页、订阅轮询和图片落盘顺序问题，本质上都属于同一类问题的不同表现。

### 2. 历史存储兼容路径还没有完全收敛

仓库当前仍然承受以下路径并存带来的兼容压力：

- `public/output/`
- `data/images`
- `file://` 风格的引用

只要这些路径长期并存，刷新、恢复、导出和迁移的行为就会持续比应有复杂度更难推断。

### 3. 测试覆盖有厚度，但还不均匀

现有测试已经覆盖到重要主干逻辑，但仍存在明确缺口，主要在：

- API route 集成测试
- 代表性 E2E 用户流程
- ComfyUI、Wikipedia、relations 这类边界场景

这意味着当前状态更接近“核心模块守得住”，而不是“完整产品链路已经在真实条件下被充分证明”。

### 4. 工程噪音正在污染信号

当前 `lint` 输出会混入 `.worktrees/comic-generation-orchestrator/...` 的 warning，而不是只反映主仓源码问题。主仓本身虽然仍是通过状态，但这种噪音会降低代码健康判断的效率。

同时，当前 `dev` 工作树也不是干净状态。这个问题不如运行时和持久化风险高，但如果长期放着，会提高后续评审和集成成本。

## 近期优先级建议

如果把这个项目当成一条工程路线来排，近期优先级应该按下面顺序走。

### 优先级 1：明确任务执行的权威状态模型

在代码和文档中明确哪些阶段以服务端为准，哪些客户端状态只是临时 UI 态。

目标不是重写系统，而是停止反复出现下面这些状态不一致：

- 页面看到的任务状态
- 落盘后的任务快照
- 队列执行状态
- 文件真正落盘完成的状态

这是当前最有杠杆的稳定性工作，因为最近很多 bug 都是它的下游症状。

### 优先级 2：继续收敛历史存储路径

继续把历史图片输出兼容逻辑往以 `data/images` 和 durable 引用为中心的主模型收敛。

这会直接减少：

- 刷新不一致
- 导出歧义
- 恢复与迁移复杂度
- 结果页边界问题

### 优先级 3：补关键集成测试和 E2E，而不是盲目追覆盖率

不建议追求泛化的覆盖率数字，而应该补那些一旦坏掉就会直接伤到用户链路的地方：

- `tasks` 与 `actions` 路由集成回归
- Result 订阅与恢复流程
- ComfyUI 与 Wikipedia 边界
- 1 到 2 条代表性 E2E：创建脚本、继续出图、刷新恢复、导出

### 优先级 4：降低工程工作流噪音

把与主仓无关的 worktree 输出排除出主仓 `lint` 视野，同时保持当前活跃分支状态更容易判断。

这个优先级低于运行时和存储层工作，但仍然值得做，因为它会提高日常反馈质量。

## 下一阶段成功标准

下一阶段的稳定性收口可以视为成功，当且仅当：

- 任务状态所有权在客户端和服务端路径之间是明确且一致的
- 图片持久化不再依赖历史双路径兼容行为
- 最高风险 API 和用户流程具备针对性回归覆盖
- `lint` 和评审输出能够清晰反映主仓，而不是被无关 worktree 污染

## 结论

ComicPedia 当前应该被视为一个“成熟但仍然偏脆”的系统：

- 已经成熟到值得继续投入
- 还没有稳定到适合最大化功能推进速度

正确的近期策略不是继续铺大功能面，而是先做稳定性收口，再扩张。
