# 2026-04-09 推广前稳定化 Track 1 设计

> Date: 2026-04-09
> Status: Draft for review
> Scope: 数据治理、可信列表、管理员修复入口、作品找回

## 目标

在不丢失任何真实创作数据的前提下，先收口推广前最伤用户信任的三类问题：

- 首页加载总作品和最近作品过慢
- 历史记录默认混入测试数据、空白作品和无意义的 `Episode N`
- 真实作品存在于 SQLite 中，但用户无法稳定地在默认列表里找到

本设计只覆盖推广前稳定化的 `Track 1`。Accuracy provider 可观测性、图片模型 API 校验、生产护栏和运营模式属于后续 `Track 2/3`。

## 背景与问题陈述

当前仓库的任务权威源是 SQLite `tasks` 表，首页和历史页通过 `/api/tasks` 读取列表。这个路径现在有两个结构性问题：

1. 列表接口复用了完整任务对象，带出了过多 `script` 内容，首页和历史页为了只显示摘要，也要承担完整脚本和面板数组的读取成本。
2. 测试任务、空脚本任务和真实用户作品共用同一张表，但默认列表没有正式作品过滤能力，导致历史页出现大量空白卡片和 `Episode N / Test` 记录。

本地数据库现状已经说明问题不是偶发脏数据，而是缺少治理边界：

- `tasks` 总量为 450
- `arc_test_*` 测试任务为 418
- `title like 'Episode %' and topic='Test'` 的记录为 266
- 另有多条 `completed` 但脚本为空的任务

与此同时，真实作品并未真正消失。例如“神农尝百草”任务仍存在于 SQLite，状态为 `completed`，图片也仍在 `data/images/...`。用户感知到的“丢失”，本质上是列表可信度和查找路径失效。

## 范围

本设计覆盖：

- 任务来源分类与历史数据兼容策略
- 首页与历史页的轻量摘要列表读取
- 管理员“维护与修复”入口
- 测试/空白任务的扫描、预览、执行删除
- 真实作品的权威检索与找回
- 相关错误处理、删除护栏和测试策略

本设计不覆盖：

- Accuracy Research Provider 的命中链路展示
- 文生图模型 API 端点校验和非 JSON 响应修复
- 生产环境 demo/seed 的硬性禁用策略
- 完整审计后台或多租户权限体系

## 核心设计

### 1. 数据模型：保留单一权威表，补任务来源字段

`tasks` 继续作为唯一权威表，不新增“正式作品表”或平行归档表。为任务补充内部来源字段 `origin`：

- `user`
- `demo`
- `test`
- `imported`
- `system`

设计决策：

- `origin` 是系统内部字段，不暴露给普通用户作为内容标签
- 现有 `tags` 继续只承担用户组织能力，不混入系统分类
- 历史数据如果没有 `origin`，默认按 `user` 处理，确保旧作品不会因缺字段被误隐藏

这样可以在不迁移作品实体关系的前提下，为默认列表、管理员修复和后续审计建立稳定分类基础。

### 2. 读路径：为首页和历史页引入轻量摘要投影

列表页不再复用完整 `GenerateTask`。新增任务摘要投影 `TaskListItem`，只返回列表渲染所需字段：

- `id`
- `status`
- `stateAuthority`
- `createdAt`
- `updatedAt`
- `reviewStatus`
- `queueSummary`
- `comfyuiRemotePendingCount`
- `scriptSummary`

`scriptSummary` 只包含：

- `title`
- `topic`
- `style`
- `panelCount`
- `coverImageUrl`

设计决策：

- 首页和历史页只调用摘要列表接口
- 结果页详情仍然读取完整任务
- 默认列表只返回 `origin=user` 的任务
- 管理员模式可切换“包含非正式任务”

这样首页统计和最近作品可以直接基于正式作品摘要数据计算，不再把整个 `script.panels[]` 拉到列表页。

### 3. 管理员修复入口：设置页下的“维护与修复”

新增管理员入口，位置在设置页体系内，例如 `设置 > 维护与修复`。该入口不出现在普通创作导航中，只承担数据治理职责。

入口包含三个动作：

- `扫描`
- `预览`
- `执行`

不做应用启动时自动清理，不做列表页静默自修复。所有危险动作必须由管理员显式触发。

### 4. 候选分类：自动删除与人工确认分层

扫描结果分为两组：

#### 可自动删除

命中强规则、且对真实作品误伤概率极低的候选，例如：

- `id` 命中 `arc_test_*`
- `topic='Test'` 且标题为 `Episode N`
- `status='completed'` 但脚本为空
- 由测试夹具明确写入的异常样本

#### 需人工确认

异常明显，但不能安全断定为垃圾数据的候选，例如：

- 标题为空，但主题不像测试语料
- 面板缺失，但任务时间和主题像真实创作
- 状态异常且脚本不完整，但存在真实图片或用户标记

设计决策：

- `可自动删除` 支持批量执行
- `需人工确认` 不支持批量硬删，只能逐条查看和手动删除
- 执行页必须显示命中规则，避免“黑盒删库”

### 5. 删除执行：预览后按固定快照执行

删除流程必须是：

`scan -> preview -> execute`

执行阶段不重新按规则动态扫描，而是使用预览阶段确认过的候选快照，避免扫描和执行之间数据库变化导致结果漂移。

删除行为包括：

- 删除 `tasks`
- 删除关联 `task_jobs`
- 删除关联图片记录
- 删除对应图片文件

返回结果必须分项展示：

- 成功删除数量
- 跳过数量
- 失败的任务 ID
- 每个失败项的原因

### 6. 作品找回：按 SQLite 权威源检索

新增“作品找回”视图，支持按以下条件查找任务：

- 任务 ID
- 标题关键词
- 主题关键词

查找结果除了基础信息外，还应明确告诉管理员为什么这条作品没有出现在默认列表：

- 是否被默认过滤为非正式任务
- 是否被清理到 `trash`
- 是否图片资源缺失
- 是否详情存在但摘要投影异常

结果页提供直接动作：

- 跳转到结果页
- 打开修复页
- 标记为正式作品
- 从 `trash` 恢复（如果后续已接入该能力）

### 7. 审计记录：记录修复动作，而不是记录所有读取

Track 1 只对破坏性或修复性动作留审计记录，不做全面运维系统。建议新增轻量维护日志表，例如 `maintenance_actions`，记录：

- 时间
- 动作类型
- 操作者标识
- 规则命中摘要
- 影响的任务 ID 列表或数量
- 执行结果

这样既能追查推广前的清理动作，又不会把当前轨道扩大成后台系统重构。

## 组件与接口设计

### 页面与组件

- 新增设置页子视图：`维护与修复`
- 新增扫描结果列表组件
- 新增删除预览确认组件
- 新增作品找回搜索组件

### 服务端接口

建议新增一组内部维护接口：

- `POST /api/admin/task-health/scan`
- `POST /api/admin/task-health/execute`
- `GET /api/admin/task-lookup`

接口职责：

- `scan`：返回候选集，分为“可自动删除/需人工确认”
- `execute`：基于预览快照执行删除
- `lookup`：按 `id/title/topic` 检索 SQLite 权威数据

### 列表接口调整

现有 `/api/tasks` 列表读取改为返回摘要投影，并支持过滤参数：

- `origin=user` 作为默认值
- 管理员模式可显式请求包含 `demo/test/system`

详情接口 `/api/tasks/[id]` 保持完整任务返回，不参与本次摘要瘦身。

## 数据流

### 首页和历史页

1. 页面请求任务摘要列表
2. 服务端仅返回 `origin=user` 的摘要项
3. 前端直接基于摘要计算作品总数、最近作品、筛选与分页
4. 用户进入结果页时，再读取完整任务详情

### 管理员扫描与清理

1. 管理员点击“扫描”
2. 服务端按规则生成候选集
3. 前端展示候选预览和命中原因
4. 管理员确认执行
5. 服务端按候选快照删除任务及关联资源
6. 记录维护日志并返回执行报告

### 作品找回

1. 管理员输入 `id/title/topic`
2. 服务端直接查 SQLite 权威表
3. 返回任务状态、来源、资源完整性和不可见原因
4. 管理员决定跳转、恢复或修复

## 错误处理

错误处理遵守两个原则：

- 列表可降级
- 删除不可误伤

列表侧：

- 首页和历史页优先读摘要接口
- 摘要接口失败时允许回退本地缓存，但 UI 必须提示“数据可能不是最新”
- 摘要构建失败的异常样本应进入管理员修复页，而不是在前端静默吞掉

修复侧：

- 任何删除都必须经过预览确认
- `execute` 返回逐项执行结果，不允许只返回一个模糊的成功/失败
- 一旦发现候选快照与当前数据库冲突，应跳过该项并报告原因，而不是强行删除

找回侧：

- 搜索结果必须区分“不存在”“被过滤”“已删除”“资源损坏”这几类状态
- 对真实作品永远优先展示只读信息，不自动改写数据

## 测试策略

### 单元测试

- `origin` 默认值与来源分类规则
- 强规则识别：`arc_test_*`、`Episode N + Test`、空脚本完成任务
- 摘要投影只返回列表所需字段，不再携带完整 `panels[]`
- 默认列表过滤仅返回 `origin=user`

### 路由测试

- 扫描接口能正确区分“可自动删除”和“需人工确认”
- 执行接口只删除明确命中的测试数据
- 删除时联动清理 `task_jobs` 和图片资源
- 找回接口支持按 `id/title/topic` 检索真实作品

### 页面回归

- 首页总作品和最近作品只统计正式作品
- 历史页默认不再出现空白 `Episode`
- 真实作品能够通过默认列表或找回入口重新出现

### 兼容性测试

- 老数据无 `origin` 时默认按 `user` 处理
- 摘要列表与结果页详情接口可以并存
- 删除测试数据不会影响真实作品的详情页访问

## 成功标准

Track 1 完成后，应满足以下标准：

- 首页和历史页默认只展示正式作品
- 默认列表中不再出现 `arc_test_*`、空白 `Episode`、空脚本完成任务
- 真实作品即使未出现在默认列表，也可以通过找回入口按权威源检索到
- 列表接口不再返回完整任务脚本，首页和历史页加载时间明显下降
- 任何危险清理动作都有预览确认和执行报告

## 风险与取舍

### 为什么不直接新建正式作品表

因为这会复制任务实体和关联资源关系，带来更高迁移和一致性成本。当前问题的根因是分类和读路径失控，不是单表模型本身错误。

### 为什么不在前端直接隐藏测试数据

只隐藏 UI 无法解决首页慢、作品找回困难和数据库持续积累垃圾的问题，也不利于推广前建立可信的运营基线。

### 为什么不做启动自动清理

自动清理最容易误伤真实数据，也不利于回溯。当前阶段更需要可审计、可预览、可人工确认的治理工具。

## 后续轨道

以下内容明确留给后续轨道，不纳入本 spec：

- Accuracy Search / Fetch provider 的命中链路展示与 fallback 可观测性
- 图片模型端点连通性和 API/网页地址混用校验
- 生产环境调试入口与 demo/seed 能力的强管控
- 更完整的管理员认证与操作权限模型
