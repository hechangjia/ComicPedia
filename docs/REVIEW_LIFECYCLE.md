# 深度复审生命周期与服务端 VLM I/O

批次开始于 2026-09-20，最终验证于 2026-09-21；证据仍保存在 `.codex/review-lifecycle-2026-09-20/`，不是误将当前日期写成前一天。实现原设计的任务权威、服务端模型与恢复边界，完整重构目标不缩小。

## 已复现并修复

真实 SQLite 配受控模型 Promise 的首轮回归为 6 失败、1 通过：复审开始跨 await 被删除后复活；换图后仍写旧评分；暂停后发布迟到评分；同 ID 恢复被旧失败覆盖；暂停/恢复后新结果被旧执行覆盖；提示词变更后写入过期诊断。原有模型 mock 无法证明这些持久化行为正确。

后续还复现并修复：pause/resume/reconcile 三个操作自身跨 await 重新插入任务；通用恢复作业 payload 可携带旧执行标识；缓存评分未区分模型；旧诊断无输入版本也被合并到新报告。

## 事务与执行归属

- DB 的 `mutateTaskReviewState` / `mutateTaskQueueState` 在 immediate 事务内读取最新任务和作业、调用同步转换、更新现有行并保存变化作业。创建复审作业与任务队列状态也在同一事务内完成。
- Review 只更新所属元数据/状态；Queue 额外允许进度与分镜状态恢复。标签、收藏、创建时间、服务端重放信息和未知 metadata 不由旧快照覆盖。删除后的调用返回空/错误，不插入任务。
- 每次 review claim 生成随机执行标识、增加尝试次数。每个 checkpoint 与提交比较当前作业状态、执行标识和脚本内容摘要。
- pause/resume/reconcile 去除复审执行标识；通用 `upsertTaskJob` 同样不恢复旧标识。仅事务内的复审 claim/commit 可保留标识。
- 结构化输入变更后，本次作业失败并提示重新开始；已暂停/替代/删除的执行直接停止，不覆盖新状态或继续发下一阶段请求。仍在排队的复审显示 running，不误报 idle。
- 每次复审既校验脚本内容，又读取所用图片的实际字节摘要。评分缓存身份包含脚本、媒体、服务地址/模型/协议（不含密钥）；同 URL 换内容或换模型不复用旧分数。无版本旧评分重新评估；无相同来源版本的旧诊断不合并成当前有效报告。相同来源的定向报告仍可合并。

这不是跨进程唯一执行锁：另一次 claim 可能让之前请求失去写入权，但两个远程请求仍可能已发出。文件系统与 SQLite 也不是一个原子事务；实际字节在读取及阶段提交前再次检查，最后一次检查到 DB 提交之间的外部文件改写仍不能证明完全消除。

## 服务端图片与模型路径

真实文件 + HTTP 集成发现旧服务端调用依赖 `/api/llm` 相对地址、`FileReader` 和浏览器图片解析；上游实际收到 0 请求，却可能生成默认 5 分并标记复审成功。

本批增加 `VisionRuntime` I/O 接口，纯评分/诊断逻辑可接受服务端实现；未向客户端 bundle 引入文件系统依赖。服务端实现：

- 从受路径边界保护的本地 file key 或 `/api/images/{key}` 读取图片，也接受限定 MIME 的 inline base64。不会把任意远程图片 URL 转为服务端抓取；这种输入明确要求先保存到作品。
- 单图片读取上限 20 MiB、所用图片合计 128 MiB；读取前检查大小，并限制实际分配，检查同 key 字节变化。此处不等同于图片完整解码/安全内容认证。
- 向已解析配置的模型地址发绝对 URL 请求，保留现有目标地址校验、拒绝重定向、120 秒超时、2 MiB 文本响应上限；错误不包含上游原始响应体。
- OpenAI-compatible/Anthropic 复用既有多模态 payload 构造；本批真正 HTTP 集成覆盖的是 OpenAI-compatible，未据此声明 Anthropic 实际服务兼容通过。
- durable review 启用 strict 模式：缺图、HTTP 错误、无效评分 JSON 等会失败，不用默认中性分数冒充成功。每图/跨图评分、诊断都能在 I/O 边界检查执行有效性。
- 图片队列单图 light check 也使用同一服务端 adapter，检查素材未被删除/替换；真实 HTTP 测试覆盖这一分支。轻量复审失败仍由图片队列现有错误策略处理，不能据此称其 UI 失败说明已全部重构。
